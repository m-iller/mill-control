# Окно капремонта мельницы

Программа считает износ узлов барабанной шаровой мельницы мокрого измельчения и подсказывает режим, при котором узлы доходят до предельного состояния одновременно. Это не система управления: ничего не регулируется, есть только расчёт и рекомендация.

Наработка мельницы до капитального ремонта — общий горизонт T. Узел i можно менять kᵢ раз за этот цикл (kᵢ = 1, 2, 3 или 4), тогда промежуточные замены попадают на моменты T/kᵢ. Цель — выработать ресурс узлов как можно полнее и остановить мельницу один раз на максимальное их число.

## Установка

Нужен Python 3.10 или новее.

```bash
python3 -m venv .venv
.venv/bin/pip install -e ".[dev]"
just setup
```

`just setup` создаёт окружение, ставит зависимости и подключает git-хуки (`git config core.hooksPath .githooks`). Если `just` нет, то же самое делает `make setup`.

Запуск окна:

```bash
.venv/bin/python -m millrepair
```

Расчёт без окна:

```bash
.venv/bin/python -m millrepair --calc
.venv/bin/python -m millrepair --optimize
.venv/bin/python -m millrepair --version
```

Файл базы по умолчанию лежит в каталоге данных пользователя (`platformdirs`, на Linux это `~/.local/share/millrepair/millrepair.sqlite`). Его можно заменить флагом `--db путь`. Обновление или удаление программы этот файл не трогает.

## Как править формулы

Ни одна физическая формула не зашита в код. Все выражения, коэффициенты, узлы и виды отказа лежат в базе и правятся на вкладке «Модель».

Формула — строка вида `k_l * A * (G/G0)**a_l`. В ней можно ссылаться на переменные режима, параметры, другие производные величины и, в формулах вида отказа, на локальные имена (`v`, `R`, `t_det`, `eta`, `t`, `consumed`, `measured`, `has_measurement`). Разрешены `+ - * / **`, унарный минус, сравнения, тернарный оператор `a if cond else b` и функции `exp, log, log10, sqrt, abs, min, max, pow, gamma, sin, cos, tanh, clip`. Константы: `pi`, `e`. `eval` не используется.

Кнопка «Проверить» ловит синтаксис, неизвестные имена (и подсказывает, чего не хватает), цикл между производными величинами и показывает пробное значение на текущих числах. Ошибочная формула не роняет расчёт: узел помечается, остальные считаются.

Над текстом формулы показана её математическая запись: дроби, степени, корни, нижние индексы и греческие буквы (`sigma_H_nom` → σ с индексом «H, nom», `mu0` → μ₀, `dTheta_nom` → ΔΘ с индексом). Запись обновляется по мере набора. Условие `a if cond else b` рисуется фигурной скобкой с двумя строками. Кнопка «Все формулы» открывает всю модель одной страницей, рядом с каждой формулой стоит её значение при текущем режиме; страницу можно сохранить в PNG и отправить руководителю. Рисует формулы mathtext из matplotlib, LaTeX в системе не нужен.

«Сохранить версию» не затирает старую формулу. У версии есть дата, комментарий и источник. Историю можно открыть, сравнить две версии и откатиться: откат создаёт новую версию со старым текстом. Сохранённый результат расчёта хранит номера версий, по которым он посчитан.

В программе можно держать несколько именованных моделей, копировать модель целиком и переключаться между ними. «Экспорт JSON» / «Импорт JSON» нужны, чтобы отправить набор формул руководителю или положить его в git.

Модель, которая попадает в пустую базу, лежит в репозитории в двух одинаковых файлах: `seed/default_model.json` (то, что удобно читать и отправлять) и `src/millrepair/data/default_model.json` (то, что программа находит через `importlib.resources` и из исходников, и из сборки). После правки скопируйте один файл в другой. Тест сравнивает их содержимое.

Коэффициенты в модели по умолчанию условные, это написано в комментариях к ним. Единицы измерения — отдельное поле у каждой величины, программа их не пересчитывает.

## Формат JSON

Корень — объект с полями `format` (сейчас 1), `name`, `description`, `criterion` (`A` или `B`), `cycle_start`, `symbols`, `units`.

Величина (`symbols`) имеет `kind`: `regime`, `parameter`, `derived` или `technology`. У переменной режима есть `value`, `min`, `max`, `adjustable`. У параметра — `value`. У производной величины и технологической формулы — `expression`. У всех есть `units`, `description`, `comment`, `source`.

Узел содержит `weight`, `multiplicity` (`null` значит «подбирать», иначе 1–4) и `failure_modes`. У вида отказа есть `measurement_quantity`, `rate_parameter` (имя коэффициента для калибровки) и `formulas` с ролями `wear_rate`, `residual`, `t_det`, `eta`, `reliability`, `t_fail`.

## Допущения, требующие проверки

Их выбрал автор программы там, где в постановке не было однозначных единиц или коэффициента. Всё это лежит в модели, а не в коде.

1. Массы мельницы, шаров и руды заданы в тоннах. В нагрузке на подшипник стоит множитель `9.81e3`, чтобы получить ньютоны. Запись `9.81 * (...)` при массах в тоннах дала бы килоньютоны.
2. `rho_pulp` — постоянная плотность пульпы в т/м³, а не функция доли твёрдого.
3. `m_charge` — постоянная масса руды в мельнице, т.
4. Формула `h_min` упрощена: гидродинамическая часть плюс гидростатический подъём. Коэффициенты `c_h` и `c_s` подобраны так, чтобы толщина получалась в метрах. Это не классическая формула Рейнольдса.
5. `p_m` считается в паскалях. `k_b` согласован с этим и со скоростью скольжения в м/с, скорость износа баббита — в мм/ч.
6. `M_nom` — производная величина `9550 * P0 / n0`, чтобы номинальное контактное напряжение совпадало с `sigma_H_nom`.
7. `P_prod` по умолчанию равен `Q`. Определение производительности нужно уточнить; формула отдельная и её можно заменить, не трогая `Q`.
8. Частота вращения `n` по умолчанию не регулируется: считается, что частотного привода нет. Границы заданы, галочку можно включить.
9. Если в журнале режима есть пропуск, износ за этот промежуток считается по текущим значениям переменных. При перекрытии периодов берётся период с более поздним началом.
10. `consumed` — износ от последнего замера этой величины (или от начала цикла, если замера нет) до момента расчёта. Остаток считает формула вида отказа.
11. Кривая P(t) узла — минимум P по его видам отказа: узел доживает до первого из них.
12. Узел попадает в окно, если `0 ≤ tᵢ − T/kᵢ ≤ δ`.
13. Критерий A для оптимизатора — одна скалярная цель: сначала максимум числа узлов в окне, при равенстве минимум недоработанного ресурса. Ограничения входят штрафом, градиентные методы не используются.
14. Для привода калибруются `L0_ins` и `N0`: через них скорость расходования зависит монотонно, это аналоги `k_l` и `k_n`.
15. Числа модели по умолчанию подобраны под мельницу класса МШЦ 3.6×5.5 так, чтобы на номинале времена отказа отличались в разы, а оптимизатор мог их сблизить. Это иллюстрация метода, не паспорт.
16. Время в базе хранится в UTC.
17. `t_fail` — момент, когда P(t) падает до `eps`. При `eps = 0.05` это время, к которому деталь уже отказала с вероятностью 95 %, и оно в 1,6–1,9 раза больше среднего ресурса `t_det`. Оптимизатор подгоняет замену `T/k` именно к `t_fail`, поэтому на графике остаточный ресурс доходит до нуля раньше плановой замены. Если ремонт нужно планировать до отказа, порог берут большим (гамма-процентный ресурс, `eps = 0.9…0.95`) — это решает руководитель.
18. Кривая узла — минимум P по видам отказа (допущение 11). Для независимых видов отказа надёжность последовательной системы равна произведению P, и оно ниже минимума: у привода на номинале порог `eps` достигается примерно на 6 % раньше, чем показывает программа.
19. Решение оптимизатора не единственное: при `w_T = 0` все точки, где все узлы попали в окно, равноценны, и разные зёрна дают разные `T` (от 12 до 29 тыс. ч на модели по умолчанию). Чтобы выбор был определённым, задайте `w_T > 0` или увеличьте `--maxiter` и `--popsize`.
20. При кратности `k > 1` новая деталь после замены считается с тем же временем до отказа, что и текущая. Если по текущей детали есть замер или износ от начала цикла, её остаток меньше, чем у новой, и оценка получается с запасом.
21. `z_cycles = 248` — число зацеплений на оборот мельницы. Зуб венца нагружается один раз за оборот, зуб шестерни — `z₂/z₁` раз (порядка 8). На результат это сейчас не влияет: `N0` подобран под целевой ресурс, но при переходе на паспортные данные пару `z_cycles` и `N0` нужно задавать согласованно.
22. Калибровка пропускает промежутки, где измеренная величина выросла: это замена детали, а не износ.

На номинале модели по умолчанию ориентиры такие: подшипники около 5500 ч, футеровка около 9000 ч, зубья около 13000 ч, изоляция около 24000 ч, патрубки около 18000 ч. Выпуск Q около 72 т/ч при Q_min = 60 т/ч.

## Тесты

Хуки лежат в `.githooks/` и включаются командой `just setup`.

- Перед коммитом: `ruff` по изменённым файлам и `pytest -m "not slow"`.
- Перед push: полный `pytest --cov` с `QT_QPA_PLATFORM=offscreen`. Если тесты падают, push отменяется.
- В крайнем случае хук можно пропустить: `git commit --no-verify` или `git push --no-verify`.

Команды:

```bash
just test       # быстрые тесты
just test-all   # полный прогон, отчёт в htmlcov/
just check      # ruff check и ruff format --check
```

`just test-all` и `scripts/ci_local.sh` — это тот же набор, который иначе гонял бы GitHub Actions: ruff и pytest с покрытием. В Actions тесты не запускаются, минуты ограничены. Порог покрытия 70% для всего, кроме каталога `ui/`.

На Windows из PowerShell, после `python -m venv .venv` и `.\.venv\Scripts\pip install -e ".[dev]"`:

```powershell
git config core.hooksPath .githooks
$env:QT_QPA_PLATFORM = "offscreen"
.\.venv\Scripts\ruff check .
.\.venv\Scripts\ruff format --check .
.\.venv\Scripts\pytest -m "not slow"
.\.venv\Scripts\pytest --cov --cov-report=term-missing --cov-report=html
```

Хуки в Git Bash на Windows ищут `.venv\Scripts`. Пути в коде и тестах собраны через `pathlib`.

Маркер `slow` стоит на оптимизаторе и интерфейсе. У оптимизатора фиксированы `seed`, `maxiter` и `popsize`, чтобы прогон оставался коротким.

## Выпуск релиза

Версия берётся из git-тега через hatch-vcs. Её показывает заголовок окна и `python -m millrepair --version`. Перед тегом сборка подставляет версию переменной `SETUPTOOLS_SCM_PRETEND_VERSION`, чтобы число в бинарнике совпало с выпуском.

### Локально, без минут Actions

1. Дописать раздел версии в `CHANGELOG.md`.
2. На Linux: `scripts/release.sh 0.1.0`. Скрипт проверяет чистое дерево и раздел в журнале, гоняет `just check` и полный набор тестов, собирает `.deb`, создаёт тег `v0.1.0`, пушит его и публикует GitHub Release с пакетом, `SHA256SUMS.txt` и текстом из журнала.
3. На Windows: `.\scripts\build_win.ps1 0.1.0`. Скрипт переключается на тег, гоняет тесты, собирает zip (и установщик Inno Setup, если в PATH есть `ISCC`) и дописывает файлы в тот же релиз.

Установщик ставит ярлык в меню «Пуск» и удаляется штатно. База пользователя при этом остаётся в каталоге данных.

Пакет Linux: `millrepair_<версия>_amd64.deb`. Файлы программы в `/opt/millrepair/`, команда `/usr/bin/millrepair`, ярлык `.desktop` и иконка 256×256. Сборка на новом дистрибутиве может не запуститься на старом из-за glibc, поэтому `packaging/build_deb.sh --docker 0.1.0` собирает пакет внутри `ubuntu:22.04`. Скрипт сам запускает бинарник с `--version` и `--calc`, затем `dpkg-deb --info` и `lintian` (предупреждения допустимы, ошибки — нет).

### Запасной путь

Если Windows-машину не открыть, релиз уже создан скриптом на Linux, а добрать бинарник нужно в облаке: вкладка Actions, workflow `release`, запуск вручную. Параметры — версия без `v` и платформы `linux`, `windows` или `both`. По тегам и push workflow не стартует. Тесты там не запускаются. Минуты Windows-раннеров на приватных репозиториях списываются с коэффициентом 2, поэтому этот путь запасной.

Workflow вызывает те же `packaging/build_deb.sh` и `scripts/build_win.ps1 -SkipTests`, а не свою копию команд.
